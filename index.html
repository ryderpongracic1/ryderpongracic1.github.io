distrikv — Distributed Key-Value Store ↗

A replicated Go key-value store for studying consistency, ambiguous failures, and recovery under fault injection.
  • Problem — preserve correctness through partial failures, including writes applied despite a failed response.
  • Decision — model ambiguous outcomes explicitly; repair with per-key sequence numbers and an idempotent WAL.
  • Correctness — chaos-tested histories remained linearizable; ~104K refused-but-applied writes converged as 373 deduplicated entries in 1–5 seconds.
  • Performance — 6,017 reads/s at p99 1.7 ms and 1,200 writes/s at p99 4.6 ms on a 3-node cluster.
Full case study on GitHub ↗
  • Throughput ceiling — 3-node Docker cluster, open-loop Poisson load, 128 workers, 256B values
    • reads 6,017/s @ p99 1.7ms · writes 1,200/s @ p99 4.6ms · mixed 3,000/s @ p99 2.5ms — zero errors, no saturation6K reads/s
    • Open-loop generator is coordinated-omission-aware; an etcd comparison harness runs the same methodology with configs disclosed
  • Consistent hash ring — owns key placement and replica set selection
    • Virtual positions per physical node on a uint32 ring; GetN(key, R) returns R distinct physical hosts
    • Raft's log replication is real (§5.3 log matching, crash-persistent, apply-on-commit) but deliberately narrow: it carries only node-health transitions, committed through its own log — so there are no dedicated liveness probes, and the ring, not the consensus log, moves data
    • Fixed an election-storm defect measured at ~1.7 terms/sec — now one election at startup and stable terms thereafter
  • LSM-Tree storage engine — leveled compaction (L0 → L1)
    • Write-stall backpressure bounds L0 growth so write floods can't starve reads
    • Bloom filters skip SSTables on point reads at a measured 0.01% false-positive rate
    • Hardened WAL — CRC32 framing, fsync per append, allocations cut 5 → 2 per append
    • 32-shard LRU block cache — Zipfian (α=1.1) vs uniform on a 500K-key flushed store: 97.2% vs 70.9% hit rate, same cluster, one flag changed97.2% zipfian hit rate
  • Per-key sequence numbering — apply-if-newer replication on WAL-persisted sequence numbers
    • Makes replica arrival-order inversions impossible by construction rather than unlikely
    • Epoch-guarded so a restarted node can't regress its counter and resurrect stale writes
  • Correctness under fault injection — Porcupine linearizability checker + a Jepsen-style chaos runner with kill-restart and stop-restart nemeses
    • 14 defects found, fixed, and pinned as regression tests — the last two the same failure shape caught twice14 defects pinned
    • Anti-entropy repair converged ~104,000 refused-but-applied writes using only 373 shipped catch-up entries — ~280× key-level dedup — in 1–5s280× dedup
    • Final gate: 4/4 consecutive chaos runs plus control all PASS with linearizable histories

stormglass — Event-Time Stream Processor ↗

A C++ event processor with keyed parallelism, event-time windows, and crash-safe checkpoint recovery.
  • Problem — keep window results correct through late events, duplicate delivery, multi-source fan-in, and crashes.
  • Decision — min-combine watermarks, align checkpoints across channels, and reject torn snapshots.
  • Correctness — 100 seeded differential runs had zero mismatches; five mid-alignment crash runs restored with zero missing or duplicated results.
  • Performance — ~8.5–9.0M records/s single-threaded; batching cut per-record hand-off overhead by 44–56%.
Full case study on GitHub ↗
  • The correctness property — an unmodified oracle, fed the same deterministic input, computes exactly the engine's drop/fire decisions
    • Single-source differential: 100 seeds × 10K records, 0 mismatches0 mismatches
    • Cross-N proof: N in {1, 2, 4, 8} × 3 disorder profiles — every N matches both the oracle and the single-threaded run on result set and drops, so parallelism is invisible to the semantics
    • Multi-source: K in {1, 2, 3} over both engines — engine_drop == oracle_drop exactly (1,312/1,312 on a K=3 heavy-tailed run, 50 seeds)143 tests
  • Multi-source fan-in — K independent sources merged ahead of an unchanged pipeline
    • Watermark is the running MIN across active channels, emitted only on strict advance so it can never regress; a resumed idle source re-pins the MIN and its records fall through the existing lateness policy — no special case
    • Idleness is a deterministic empty-pull timeout, never wall-clock — the whole reason the oracle can replay the merged trajectory at all
    • Real K-way Chandy-Lamport barrier alignment: the Nth merged barrier lands at exactly N·Σ(intervals), which is a direct proof that no record leaked past a channel's barrier and none went missing
    • Idle channels are excluded from the alignment set — without that, an active channel blocks forever on a quiet source (proven as a liveness test, not assumed)
  • Keyed parallelism, shared-nothing — records hash-routed by FNV-1a(key) % N so each worker owns a disjoint slice of state
    • Distributed checkpointing is all-or-nothing: a partial partition set is a torn global checkpoint and is never restored from
    • Snapshot restore costs 1.73 ms — reported separately from the toy source's O(offset) replay so the harness cost never masks the real one1.73 ms restore
  • Crash recovery under the nastiest timing — fork + SIGKILL landed mid-barrier-alignment, with epoch N never emitted
    • Restore falls back to the last fully-aligned checkpoint: 5/5 runs, 0 missing, 0 duplicated0 missing
    • Plus 20 between-checkpoint kills, 6 mid-checkpoint, and a partitioned torn-checkpoint nemesis at N in {2, 4} — all 0 missing
  • Measured honestly, including where it doesn't hold up
    • Single-threaded core ~8.5–9.0M rec/s on a quiet box; an earlier 1.8M figure was measured under contention and is retracted rather than quietly dropped
    • The SourceMerge wrapper costs ~11% where the noise floor is low enough to resolve it — and that cost does not grow with fan-in (K=3 outruns K=1 on both machines, since higher K coalesces watermark advances)
    • Alignment at ~10 epochs is below the run-to-run variance — stated as bounded, not free, because the sign of the median delta flips between runs
    • The N≥4 scaling curve regressed; per-record Router hand-off was the cause, and batching cut that overhead 44–56% — the multicore re-measurement is still pending and is labeled as such
  • Cross-platform discipline — std::uniform_int_distribution is implementation-defined, so libstdc++ and libc++ generate different streams and different absolute counts (1,312 vs 1,241). The invariant isn't the count, it's engine == oracle on each platform independently — verified on both

vexq — Vectorized SQL Query Engine ↗

A Go analytical query engine spanning columnar storage, SQL planning, and vectorized parallel execution.
  • Problem — build a complete analytical engine, then identify what actually limits parallel queries.
  • Decision — profile first; target I/O and allocation pressure rather than microbenchmark-friendly SIMD.
  • Correctness — a 72-query oracle passes across serial, parallel, optimizer-off, and stacked-filter paths.
  • Performance — join-build allocations fell from 1.2M to 1.5K per operation; Q1 reached 8.6× on 14 cores and 22 ms versus DuckDB's 19 ms.
Full case study on GitHub ↗
  • The ceiling — vs DuckDB on TPC-H SF1 (6M lineitem rows), decomposed into per-core efficiency and end-to-end throughput
    • Q1 all cores: 22 ms vs 19 ms steady-state — within 1.2× — and it matches DuckDB's 24 ms cold-start outrightwithin 1.2× of duckdb
    • Single-threaded Q1 193 ms vs 159 ms, also 1.2× per-core; the gap widens on the join-heavy queries — Q3 2.2×, Q12 2.9×
    • The caveat: DuckDB runs ARM64 here, without its strongest AVX-512 paths — same-machine and fair, but not a claim of parity
  • The floor — vs SQLite, 3.0–18.4× across all four benchmarked queries3.0–18.4× sqlite
    • Q3 (3-table join) 18.4× · Q1 11.4× · Q6 5.7× · Q12 3.0× — a sanity floor, not a headline: beating a row-store on OLAP scans is the expected result
  • The .vxq columnar format — written from the byte layout up
    • Per-row-group zone maps skip entire row groups before any block I/O, driven by pushed-down predicates
    • Strings dictionary-encoded so equality collapses to integer comparison in the filter hot loop — and to integer-keyed aggregation in GROUP BY
    • CRC32 block integrity, append-only manifest, atomic temp+rename writes — the same durability spine as distrikv — plus an fsck that validates CRCs, footer, and zone maps
  • Vectorized Volcano execution — 1,024-row batches sized to saturate L1 and amortize operator dispatch
    • Selection-vector filters with no allocation on the hot path; Project lazily materializes through the selection vector
    • Pratt-precedence parser → logical plan → rule-based optimizer → physical plan, with predicate pushdown and column pruning that reaches through joins, not just scans
    • Morsel-driven work-stealing scheduler; radix-partitioned parallel join build feeding a morsel-parallel probe and partial-aggregate merge
  • Parallel scaling: the GC was the bottleneck, and I proved it before touching anything
    • A GOGC ablation isolated Go's garbage collector at 26–50% of parallel wall time — diagnosis first, not a guess
    • Allocation campaign — flat open-addressed join table, per-worker pipeline reuse, scratch-buffer pooling — cut join-build allocations 1.2M → 1.5K per op1.2M → 1.5K allocs
    • GC's share fell to 0–19%, lifting Q1 to 8.6× on 14 cores — about 86% of the realistic 10-P-core ceiling8.6× on 14 cores
    • Stated like-for-like (GOGC off on both sides) that's 4.4–8.8× across the four queries — the flattering number and the strict one, both published
  • Correctness — a 72-query golden oracle against a naive row-at-a-time reference evaluator72/72 × 4 paths
    • Run across four execution paths — serial, parallel, optimizer-off, stacked-filter — all under -race in CI, 72/72 on every path
    • All four TPC-H results verified identical to SQLite in-harness (Q6's SUM to 1e-9 relative tolerance); canonical Q6 matches DuckDB exactly
  • Optimizations measured and then declined — the part that usually goes unpublished
    • In-engine SIMD profiled at a ~1.03× end-to-end ceiling and probe-stream partitioning at ~1.005×: both cut, because serial wall time is dominated by pread syscalls and page management, not compute
    • An isolated C++/AVX2 kernel study put the raw SIMD filter ceiling at 3.3× — real in a microbenchmark, and still not worth shipping end-to-end3.3× simd ceiling
    • So the honest remaining wins are I/O-side — late materialization and adaptive compression — and both are still open
